# 하루치 업무 기록 작성

한 날짜의 업무 기록을 만드는 절차와 작성 규칙이다. 날짜별 서브에이전트는 이 문서 하나만 읽으면 된다. `<skill-base-dir>`는 이 스킬의 base directory다.

## 절차

1. 템플릿 `~/.daily-work-log/daily-work-log-template.md`를 읽는다.
2. 수집 스크립트를 한 번 실행한다. 옵션은 스크립트가 `~/.daily-work-log/config.json`에서 읽는다.

   ```bash
   python3 <skill-base-dir>/scripts/build_day_evidence.py --date YYYY-MM-DD
   ```

   출력의 `candidates`가 0이면 Markdown을 만들지 않고 `saved: none`으로 반환한다.
3. 출력의 `evidence` 경로(`~/.daily-work-log/YYYY/YYYY-MM-DD/evidence.md`)를 Read로 첫 줄부터 마지막 줄까지 읽는다. 한 번에 다 들어오지 않으면 `offset`으로 이어서 읽는다. `head`, `cut`, `grep`으로 줄이거나 일부만 읽지 않는다.
4. 최종 Markdown을 써서 `<log-root>/YYYY/MM/YYYY-MM-DD.md`에 저장한다.
5. 아래 "반환 형식"으로 결과를 돌려준다.

지켜야 할 것:

- 사용자에게 묻지 않는다. 판단이 애매한 항목도 기록에 넣고 `notes`에 적는다.
- 그 날짜의 중간 산출물 디렉터리와 최종 Markdown 한 파일만 쓴다. `config.json`과 템플릿은 쓰지 않는다.
- 근거를 따로 파일로 남길 때는 그 날짜의 중간 산출물 디렉터리 안에만 둔다. 다른 날짜의 서브에이전트가 병렬로 돈다.

## 근거 파일 읽는 법

`evidence.md`는 표시 후보 전체의 근거다. 맨 위에 `impact-items`와 후보 목록이 있고, 후보마다 `## 후보 <번호> | <top|other> | <제목>` 절이 있다.

- 절 머리의 `작업 폴더`, `커밋·푸시·PR 명령`, `고친 파일`, `응답에 나온 링크`는 도구 호출 기록에서 뽑은 값이다. 참조 슬롯과 `## Impact`의 근거로 쓴다.
- 작업 단위는 시간순이다. `- 시작 시각 | 사용자 요청` 다음 줄의 `-> `가 그 단위의 마지막 응답이다. 응답 줄이 없으면 응답 없이 끝난 단위다.
- 응답은 260자에서 잘린다. 세션의 마지막 단위와 커밋·푸시·PR 단위만 1,200자까지 남는다.
- 후보 제목은 첫 사용자 요청 문장이다. 최종 Markdown의 항목 제목은 내용을 보고 새로 쓴다.

`evidence.md`만으로 무슨 일인지 판단할 수 없는 후보만 원본 세션을 연다. 세션 파일 경로는 같은 폴더의 `second-pass-digest.json`에서 그 후보의 `evidence_paths.session_files`로 찾는다. 열어도 알 수 없으면 기록에 넣되 요약에 근거가 약하다고 적는다.

스크립트 출력은 확정 문장이 아니라 근거다. 사실과 추정을 나눠 쓰고, 근거가 없는 내용은 지어내지 않는다.

## 필수 체크리스트

1. 표시 후보를 임의로 빼지 않는다. 모든 후보가 어느 한 항목에 들어간다.
2. 같은 주제의 후보는 한 항목으로 합친다. 같은 Jira 티켓의 작업, 같은 repo에서 이어진 작업, 포크 세션과 원래 세션, 추가 지시 세션과 원래 작업이 여기에 해당한다. 주제가 다르면 합치지 않는다. 한 후보는 한 항목에만 넣는다.
3. 같은 대상에 대한 기록이 여러 번 나오면 시간순으로 마지막 작업 단위를 기준으로 쓴다. 커밋·머지·배포 같은 진행 상태뿐 아니라 결정, 결론, 수치, 남은 일도 같다. 앞의 결과가 뒤에서 바뀌었으면 뒤의 것을 따르고, 앞의 것은 진행 과정으로만 남긴다.
4. 원인 규명, 결론, 확정한 결정이 있으면 그 항목의 `요약:`과 `## Impact`의 결정사항에 남긴다. 구현 설명 속에 묻어 두지 않는다.
5. frontmatter 4개 필드를 채운다. `summary`는 한 문장으로 쓰고, `tags`는 나중에 검색할 핵심 키워드 10~15개로 쓴다.
6. `impact-items`가 있고 근거가 있으면 `## Impact` 섹션을 쓴다.
7. `## 한눈에 보기` 표에 합친 뒤의 모든 항목을 넣는다.
8. 모든 항목마다 `###` 섹션을 쓴다. 각 섹션에는 `요약:`과 `- 구분:`을 두고, 근거에 repo·파일·링크가 있으면 참조 슬롯을 채운다.
9. 모든 항목마다 상세(맥락, 진행 과정, 판단 근거, 남은 일)를 자유 형식 영역에 쓰고, `<!-- 이 아래는 자유 형식 -->` 주석 라인은 지운다.
10. 항목이 많아도 위 단계를 줄이거나 생략하지 않는다.

## 필수 Frontmatter

```yaml
---
date: YYYY-MM-DD
type: daily-work-log
summary: ""
tags: []
---
```

이 네 필드는 필수다. 제거하거나, 이름을 바꾸거나, 다른 스키마로 대체하지 않는다.

- `type`의 허용값은 `daily-work-log`, `decision-record`, `trouble-shooting`, `learning-note` 네 가지다. 일일 업무 기록은 항상 `daily-work-log`로 둔다. 일일 업무 기록을 모아 보는 기준은 `tags`가 아니라 이 값이다.
- `tags`는 검색 키워드다. "나중에 이 문서를 검색한다면 어떤 키워드로 찾을까?"를 기준으로 정한다. 고정 목록으로 제한하지 않으며, `daily-work-log`를 의무적으로 넣지 않는다.

## 최종 Markdown 구조

이 문서는 한 번 쓰면 끝나는 문서다. 이후에는 사람이 다시 읽거나 에이전트가 검색한다. 위쪽은 빠르게 훑는 요약, 아래쪽은 자유 형식 상세인 2단 구조를 유지한다.

1. frontmatter 바로 아래에 `# YYYY-MM-DD 업무 기록` 제목을 둔다.
2. `impact-items`가 있으면 제목 바로 아래에 `## Impact`를 둔다. 템플릿 내용과 무관하다. 규칙은 아래 "Impact 섹션"을 따른다.
3. 첫 본문 섹션은 `## 한눈에 보기`다. 아래 표를 둔다.

   ```markdown
   | 구분 | 제목 | 요약 |
   |---|---|---|
   ```

4. 표 바로 다음에 항목을 `### 항목 제목`으로 이어 쓴다. 별도의 `## 작업 요약` 섹션은 만들지 않는다.
5. 모든 `###` 항목 뒤에 자유 형식 상세를 쓴다.

각 `###` 항목은 아래 순서를 따른다.

1. `요약:` — 필수. `###` 제목 바로 아래에 둔다. 무엇을 왜 했고 어떻게 판단했는지, 나중에 이 항목만 읽어도 기억을 복원할 수 있게 쓴다.
2. `- 구분:` — 분석/문제해결/결정 같은 대표 성격 하나.
3. 참조 목록 — `코드 경로`, `관련 파일`, `관련 링크` 슬롯 중 필요한 것만 쓴다. 2-depth list까지 허용한다.

```markdown
### API 응답 정책 정리

요약:
- `order-api`의 응답 정책과 예외 흐름을 확인하고 일지에 남길 수준으로 정리했다.

- 구분: 분석
- 코드 경로
  - `order-api` git repository
- 관련 파일
  - `order-api` `OrderController.java`, `ErrorResponse.java`
  - /Users/me/dev/example-project/_inbox/api-response-plan.md
- 관련 링크
  - API design note(응답 정책 참고): https://example.com/api-design
```

맥락, 진행/확인, 판단/배운 점, 결론, 남은 일 같은 상세 소제목은 `###` 항목 안에 고정 슬롯으로 넣지 않는다. 상세는 템플릿의 `<!-- 이 아래는 자유 형식 -->` 마커 아래 영역에 자유 형식으로 쓴다. 이 마커는 요약 영역과 상세 영역을 나누는 작업용 경계다. 최종 저장본에서는 마커 줄을 지우고 그 아래 내용만 일반 본문으로 남긴다.

## 참조 표기 규칙

참조는 "나중에 다시 찾을 수 있는 최소 표기"를 기준으로 세 종류로 나눈다.

- **git repo로 관리되는 소스코드**: full path를 쓰지 않는다. 코드 경로는 `` `repo-name` git repository ``, 파일은 `` `repo-name` `FileName.java` `` 형태로 쓴다.
- **로컬 전용 파일**: git이나 온라인 어디에도 없어서 local path 없이는 다시 찾을 수 없는 파일만 절대 경로로 쓴다.
- **인터넷 링크**: `링크 명(요약): URL` 형태로 쓴다.

repo 이름, 파일명, 명령어, 코드 식별자, 설정 키 같은 기술 식별자는 본문에서도 백틱으로 감싼다.

긴 원문 발췌보다 다시 찾아볼 수 있는 참조를 우선한다. 커밋 hash와 테스트 명령은 필요할 때만 짧게 쓴다.

Claude/Codex 세션 파일(`~/.claude/projects/...`, `~/.codex/sessions/...`)은 언제든 지워질 수 있으므로 최종 Markdown에 참조로 남기지 않는다.

## Impact 섹션

`evidence.md` 맨 위의 `impact-items`는 사용자가 매번 문서 맨 위에서 보고 싶은 항목이다. 줄마다 `이름: 찾는 기준`이다.

- `impact-items`가 없으면 `## Impact`를 만들지 않는다.
- 라벨과 순서는 `impact-items`의 이름과 순서를 그대로 쓴다. 각 라벨은 `- **{name}**` 형태로 쓴다. 찾는 기준은 판단에만 쓰고 최종 Markdown에 옮기지 않는다.
- 하루치 항목 전체를 가로지르는 요약이다. 근거를 읽으면서 라벨마다 해당하는 것을 함께 모은다.
- 근거를 찾지 못한 라벨은 생략한다. 모든 라벨이 비면 `## Impact` 섹션 자체를 생략한다. 근거가 없으면 지어내지 않는다.
- 근거가 repo에 종속된 항목(PR/MR 기록, git branch)은 repo별로 묶는다. 표기는 "참조 표기 규칙"을 따른다.

```markdown
## Impact

- **Jira Ticket**
  - PROJ-1234, PROJ-1250
- **PR/MR 기록**
  - `order-api`: `feature/PROJ-1234-refund` → PR #482 (merged)
  - `payment-api`: `fix/PROJ-1250-timeout` → MR !210 (open)
- **최종 개발 결정 사항**
  - API 응답 정책은 기존 구조를 유지하고 예외 흐름만 추가하기로 결정함
```

## 작성 언어

본문은 한글로 쓴다. frontmatter key, 고정 `type` 값, `tags`, 파일 경로, 명령어, 코드 식별자, 기술 용어처럼 영어가 더 자연스러운 항목은 영어를 유지한다.

## 안전 규칙

- 인증 정보, 원본 private log, 고객 식별자, 회사 소스코드, 운영 데이터 원문, Slack/DM 원문 전문을 업무 기록에 그대로 복사하지 않는다. `## Impact`에도 같다.
- 근거 자료는 높은 수준으로 요약해 쓴다.

## 반환 형식

```text
date: YYYY-MM-DD
saved: <최종 Markdown 절대 경로 | none>
items:
- <후보 번호, 합쳤으면 쉼표로 모두> | <top|other, 섞이면 top> | <구분> | <제목> | <한 줄 요약>
impact:
- <name>: <근거 건수>
checks:
- template: <done | skipped>
- evidence_lines: <읽은 마지막 줄 번호>/<스크립트가 출력한 lines>
- candidates: <items에 넣은 후보 수>/<스크립트가 출력한 candidates>
- item_sections: <### 항목 수>/<items 수>
- reference_slots: <참조 슬롯이 있는 항목 수>/<items 수>
- free_form_detail: <상세를 쓴 항목 수>/<items 수>
notes: <근거가 약한 항목, 실패한 단계, 참조 슬롯이 없는 항목과 그 이유. 없으면 none>
```

표시 후보가 없으면 `saved: none`과 빈 `items:`를 돌려준다.
