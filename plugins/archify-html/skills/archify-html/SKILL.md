# archify-html

넘겨받은 내용을 **HTML 하나**로 만든다. 노드, 화살표, 테이블, 컬럼, 흐름을 새로 조사하거나 추측하지 않는다.
내용이 부족하면 채워 넣지 말고 비워 두거나 미확인으로 표시한다.

이 파일은 모든 종류가 지키는 **공통 규칙**과 **지원하는 화면 종류**만 담는다. 종류별 데이터 스키마와 작성 규칙은 `kinds/` 의 파일을 읽는다.

## 지원하는 화면 종류

데이터(`data.json`)의 최상위 `kind` 가 종류를 정한다. 생략하면 `architecture` 이다.

| kind | 이럴 때 고른다 | 규칙·스키마 | 템플릿 | 예제 |
| --- | --- | --- | --- | --- |
| `architecture` | 서비스·API 사이의 호출 관계, 경로별 DB 읽기/쓰기, 외부 호출을 한 장의 지도로 보여준다. 박스에 마우스를 올리면 상세 팝업이 뜬다. | `kinds/architecture-map.md` | `templates/architecture.html` | `examples/order-flow.json` |
| `data-model` | 테이블 구조, 처리별(지급·사용·회수 등) 테이블 변화, 같은 데이터가 화면마다 다르게 노출되는 변환 규칙을 기술 문서로 정리한다. | `kinds/data-model-doc.md` | `templates/data-model.html` | `examples/data-model-example.json` |
| `tabs` | 위 두 종류로 만든 문서 여러 개를, 맨 위에 고정되는 탭 하나의 HTML 로 묶어 한 페이지에서 오가며 본다. | `kinds/tabs.md` | `templates/tabs.html` | `examples/tabs-example.json` |

종류가 애매하면 묻는다. 기준은 하나다. **호출과 경로가 핵심이면 architecture, 데이터의 모양과 상태 변화가 핵심이면 data-model** 이다. 한 요청에 둘 다 필요하면 종류별로 파일을 따로 만들고, 한 페이지에서 오가며 봐야 하면 `tabs` 로 묶는다. `tabs` 는 새 내용을 만들지 않는다. 탭에 들어갈 문서의 데이터를 먼저 만든 뒤 묶는다.

## 하지 않는 것

- 코드 읽기, 위키·DB·로그 조회, 에이전트 병렬 감사 (필요하면 이 스킬 전에 다른 방법으로 끝낸다)
- 내용의 사실 여부 판단. 받은 그대로 옮긴다. 단, 앞뒤가 안 맞으면 만들기 전에 묻는다.
- 별도의 `archify` 스킬을 포함한 다른 다이어그램 도구 의존. 이 스킬은 자기 템플릿과 스크립트만 쓴다.

## 순서 (공통)

1. **종류 선택** — 위 표에서 `kind` 를 정하고, 해당 `kinds/*.md` 를 읽는다. `tabs` 는 탭에 넣을 문서의 종류별 파일도 함께 읽는다.
2. **입력 정리** — 받은 내용을 그 종류의 스키마에 맞는 JSON(`data.json`)으로 옮긴다. 산문으로 받았다면 종류의 구성 요소(노드·화살표·DB 항목, 또는 테이블·컬럼·흐름)로 쪼갠다.
3. **생성**
   ```bash
   python3 <skill>/scripts/render.py data.json out.html --shot check.png
   ```
   - `--size 1100,4400` 으로 스크린샷 창 크기를 정한다. 기본은 `1560,1000` 이라 긴 문서는 위쪽만 찍히므로 세로를 키운다.
   - `--hash n=<노드id>` 는 그 노드의 팝업을 연 채로 찍는다(`architecture`). `tabs` 는 `--hash <탭id>` 로 그 탭을 연 채로 찍는다.
   - `--open` 은 브라우저로 연다. Chrome 이 없으면 스크린샷은 건너뛴다.
4. **확인** — 스크린샷에서 겹침, 글자 잘림, 표 열 어긋남, 하단의 에이전트용 텍스트를 본다. `ERROR:` 는 JSON 을 고친다. `WARN:` 은 종류별 문서의 안내를 따른다.
5. **전달** — 출력 경로와, 내용에서 미확인으로 둔 항목을 알린다. 요청이 없으면 커밋·공유는 하지 않는다.

## 공통 규칙

### 내용

- 받은 내용에 없는 항목, 호출, 근거를 만들어 넣지 않는다.
- 확인하지 못한 것은 확인하지 못했다고 쓴다. 추정과 확인은 섞어 쓰지 않는다. architecture 는 `stub` 노드와 `unk` 화살표로, data-model 은 문장으로 밝힌다.
- **코드 줄번호는 쓰지 않는다.** `Foo.java:41`, `Foo.java:41-52` 형태를 근거와 설명 어디에도 넣지 않는다. 코드가 바뀌면 틀어지기 때문이다. 파일명·클래스명·메서드명까지만 쓴다(예: `OrderRepository.save`). 받은 내용에 줄번호가 섞여 있으면 지우고 만든다. `render.py` 가 모든 종류에서 이 형태를 오류로 막는다.
- 키, 토큰, 비밀번호, 개인정보(유저 식별값 포함)는 넣지 않는다. 받은 내용에 섞여 있으면 빼고 알린다.
- 실제 데이터와 설명용 가상 값을 섞을 때는 반드시 구분해 표시한다(data-model 의 `실제` / `예시` / `신규` 태그).

### 문체

- 문서 문장은 개조식 평서문(`~한다`, `~이다`)으로 쓴다. 비유, 구어체, 존댓말(`~해요`)을 쓰지 않는다.
- 역할 이름은 한 번 정하면 문서 전체에서 같게 쓴다(예: 테이블 역할명을 `카테고리`, `지급 건`, `로그` 로 정했으면 다른 말로 바꿔 부르지 않는다).
- 쉬운 설명(ELI5)을 명시적으로 요청받았을 때만 풀어서 쓴다. 이 경우에도 사실 표기 규칙은 그대로 지킨다.

### 화면

- 결과 HTML 은 **외부 의존이 없는 단일 파일**이다. 외부 폰트, CDN 스크립트, 이미지를 쓰지 않는다.
- 색은 토큰으로 정의하고 라이트·다크를 모두 지원한다. 시스템 설정(`prefers-color-scheme`)과 명시 선택(`data-theme`) 모두에서 `body` 배경을 토큰으로 정한다.
- **다이어그램(SVG)은 화면 폭이 아니라 원래 크기(viewBox 폭을 CSS px)로 그린다.** `width: 100%` 로 고정하면 브라우저 줌·핀치가 크기에 반영되지 않는다. 화면보다 넓으면 다이어그램 영역 안에서만 가로 스크롤한다. 보조 컨트롤(`−`, `+`, `100%`, `맞춤`)을 함께 둔다. 범위는 40%~300%이고, `맞춤`은 화면 폭에 맞춘다.
- 표와 다이어그램만 화면보다 넓어질 수 있고, 각자 `overflow-x: auto` 영역 안에 둔다. 문서 전체가 가로로 스크롤되면 안 된다.
- 데이터의 문자열은 모두 이스케이프해서 넣는다. 데이터에 HTML 을 넣지 않는다.
- 문서는 `tabs` 에 들어갈 수 있어야 한다. 그래서 템플릿은 `<style>` 하나와 본문 뒤 `<script>` 하나만 가지고, 문서 전체용 CSS 는 `:root` 와 `body` 로만 쓴다(`kinds/tabs.md` 의 문서 쪽 제약).

### 하단 에이전트용 텍스트

- 문서 아래에 `에이전트용 텍스트` 영역이 항상 생긴다. 화면 내용을 평문으로 옮긴 것이다.
- `render.py` 가 **데이터에서 자동 생성해 HTML 소스에 그대로 넣는다.** 같은 내용을 따로 쓰지 않는다. JS 없이 파일을 읽는 에이전트도 `<pre id="agenttext">` 에서 읽을 수 있다.
- 사용자는 영역을 드래그해서 복사하거나 `전체 복사` 버튼을 누른다.
- `foot` 는 이 텍스트에 들어가지 않는다. 결론, 해석, 특정 이슈는 `foot`(또는 data-model 의 `callouts`)에 쓰고, 구조 자체만 본문 필드에 쓴다.

### 유지보수

- 문서를 수정해 다시 만들 때는 `meta.ver` 날짜를 그날로 올린다. 날짜를 안 주면 오늘 날짜가 들어간다.
- 템플릿을 바꾸지 않고 데이터만 바꿔 반복 생성한다. 템플릿을 고칠 때는 `scripts/test_render.py` 를 함께 갱신하고 `python3 -m unittest test_render` 로 확인한다.
- 이 스킬이 담는 예제는 가상 도메인만 쓴다. 실제 서비스의 테이블명, 식별자, 값을 예제나 규칙 문서에 넣지 않는다.
