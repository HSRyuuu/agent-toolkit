# data-model — 테이블 스키마 · 처리 흐름 · 화면 노출 문서

테이블 구조와, 처리(지급·사용·회수 등)가 일어날 때 테이블이 어떻게 바뀌는지, 같은 데이터가 화면마다 어떻게 다르게 보이는지를 하나의 기술 문서로 정리한다. 공통 규칙은 `../SKILL.md` 를 따른다.

- 템플릿: `templates/data-model.html`
- 예제: `examples/data-model-example.json` (가상의 리워드 포인트 도메인, 모든 기능을 한 번씩 쓴다)
- `kind` 는 `"data-model"` 로 쓴다.

## 문서 구성

위에서 아래로 읽히는 세 장과 꼬리 영역으로 이루어진다. 데이터가 없는 장은 화면에서 숨겨진다.

1. **스키마** — 테이블 개요 카드, 공식(선택), 관계도(SVG), 컬럼 사전
2. **처리 흐름별 테이블 변화** — 탭으로 흐름을 고르면 흐름마다 바뀌는 테이블 행을 보여준다
3. **화면 노출 로직** — 원본 행과, 화면별로 변환된 결과를 토글로 비교하고 변환 규칙을 나열한다
4. **꼬리** — 경고(`callouts`), 읽는 법(`foot`), 근거(`meta.basis`), 에이전트용 텍스트

## 데이터 스키마

```jsonc
{
  "kind": "data-model",
  "meta": { "title": "탭 제목", "eyebrow": "작은 머리말", "heading": "문서 제목(생략하면 title)",
            "lead": "한 단락 개요", "basis": "근거 문장", "ver": "2026-10-21",
            "sections": { "schema": "1. 스키마", "flows": "2. 처리 흐름별 테이블 변화", "views": "3. 화면 노출 로직" } },  // 전부 선택
  "overview": { "formula": "잔액 = SUM(...) WHERE ...", "note": "개요 아래 보충 문장" },                                  // 선택
  "tables": [ {
    "id": "lot", "name": "reward_lots", "role": "적립 건", "tone": "a",        // tone: a b c d. 테이블마다 색이 정해진다
    "where": "shop", "summary": "개요 카드 문장", "indexes": "인덱스: user_id, rule_id",
    "pos": [0, 1],                                                              // 선택: 관계도 격자 위치 [열, 행]
    "columns": [ { "n": "remaining", "t": "int", "d": "**현재 잔여액.** 설명", "key": true, "er": true } ]
  } ],
  "relations": [ { "from": "rule", "to": "lot", "label": "적립 시 규칙", "card": "1:N" } ],
  "flows": [ {
    "id": "earn", "label": "적립", "tag": "real", "tagLabel": "실제 데이터", "who": "누가 어떤 처리를 하는가",
    "tables": [ { "ref": "lot", "cols": ["id", "remaining"], "num": [1],
                  "rows": [ { "op": "upd", "c": ["9001", "3,000 → 0"] } ] } ],
    "notes": ["문장", "문장"]
  } ],
  "views": {
    "lead": "비교 설명",
    "source": { "title": "원본: reward_entries", "cols": ["id", "delta"], "rows": [ { "tag": "real", "c": ["7001", "+3,000"] } ] },
    "tabs": [ { "id": "admin", "label": "관리자 목록", "cols": ["ID", "포인트"], "num": [1],
                "rows": [ { "tag": "ex", "c": ["7001", "+3,000"] } ],
                "note": "변환 결과 설명", "rulesTitle": "관리자 목록 변환 규칙", "rules": ["규칙", "규칙"] } ]
  },
  "callouts": [ { "title": "경고 제목", "body": "경고 본문" } ],
  "foot": [ { "title": "읽는 법", "items": ["문장"] } ]
}
```

### 필드 규칙

- `tables[].tone` 은 `a b c d` 이다. 한 테이블은 개요 카드, 컬럼 사전, 관계도, 흐름 표 캡션에서 모두 같은 색이다.
- `columns[].key` 가 `true` 이면 컬럼 사전에서 행이 강조된다. `er` 가 `true` 이면 관계도 박스에 나온다. `er` 가 하나도 없으면 앞의 5개가 나온다.
- 관계도는 2열 격자(테이블이 7개 이상이면 3열)로 자동 배치한다. 선이 박스를 가로지르면 `tables[].pos` 로 위치를 정한다. 테이블이 7개 이상이면 `WARN:` 이 나온다.
- `relations[].card` 는 `"1:N"` 처럼 콜론 하나로 쓴다.
- `flows[].tag` 는 `real`(실제 데이터), `ex`(예시), `new`(신규·미배포) 이다. `tagLabel` 로 배지 문구를 바꿀 수 있다.
- `flows[].tables[].rows[].op` 는 `ins`(INSERT, 초록), `upd`(UPDATE, 노랑), `same`(변경 없음) 이다. 행의 칸 수는 `cols` 와 같아야 한다. 다르면 오류이다.
- 칸 값이 `a → b` 형태이면 변경 전후로 강조된다. `num` 은 숫자 칸의 위치(0부터)이며 오른쪽 정렬된다.
- `views.tabs[].rows[].tag` 는 `real`, `ex`, `new` 이다. 변환 결과(`rows`)는 **작성자가 규칙대로 미리 계산해 넣는다.** 렌더러는 변환을 계산하지 않는다.
- 문자열에서는 `` `코드` `` 와 `**굵게**` 만 쓸 수 있다. 그 밖의 HTML 은 이스케이프된다.

## 작성 규칙

### 스키마

- 컬럼 사전의 `d` 는 한 문장으로 쓴다. 값의 의미(예: `0 적립, 1 사용, 2 회수`)와 제약(예: `컬럼 타입이 int(최대 2,147,483,647)이다`)을 굵게 강조한다. 제약은 나중에 장애로 이어지기 쉬우므로 빠뜨리지 않는다.
- 같은 이름처럼 보이는 식별자는 어디에 쓰이는지 구분해 적는다(예: 목록의 ID 컬럼 값과 회수 API 의 식별자가 다른 경우).
- 외래키가 없으면 `overview.note` 나 개요 문장에 "참조 관계는 애플리케이션 규약이다"라고 쓴다.
- 확인한 스키마(컬럼, 타입, 인덱스)만 적는다. 확인하지 못한 컬럼은 만들지 않는다.

### 처리 흐름

- 흐름 하나는 처리 하나이다(적립, 사용, 취소 복구, 회수, 소멸). 흐름마다 어떤 테이블의 어떤 행이 INSERT, UPDATE 되는지를 표로 보여준다.
- 행을 만들지도 바꾸지도 않는 처리(예: 소멸)도 흐름으로 둔다. `rows` 를 비우거나 `same` 행을 두고 `who` 에 근거를 쓴다. 코드에서 기록하는 곳을 찾지 못했다면 "찾지 못했다"고 쓴다.
- 실제 운영 사례를 쓰면 `tag: "real"`, 가상 값이면 `ex`, 아직 배포 전이면 `new` 로 구분한다. 한 흐름 안에서 실제 값과 가상 값을 섞지 않는다. 식별 가능한 유저 값은 넣지 않는다.
- `notes` 에는 표만으로 읽히지 않는 규칙을 쓴다: 차감 순서, 고정된 값(코드에 박힌 카테고리 번호), 알려진 한계, 예외 경로.
- 한 번의 처리가 여러 행으로 쪼개지는 경우(예: 지급 건이 잘게 나뉘어 한 주문이 수백 행)는 실제 규모를 `notes` 에 쓴다. 그룹핑이 왜 필요한지의 근거가 된다.

### 화면 노출

- 원본 행(`views.source`)은 변환 규칙의 입력이다. 각 화면 탭은 같은 행을 규칙대로 변환한 결과이다.
- 화면 탭마다 `rules` 를 쓴다. 규칙에는 그룹핑 기준, 표시 컬럼의 출처, 값 대체 규칙(예: 저장값이 0이면 다른 컬럼으로 대체), 제외 조건을 포함한다.
- 변환 결과에 원본과 다른 값이 나오면 `note` 에 그 이유를 쓴다.
- 코드를 읽어서만 알아낸 동작은 `callouts` 나 `note` 에 "코드 분석 결과이며 운영 화면에서는 검증하지 못했다"처럼 검증 수준을 밝힌다.

### 문체와 표기

- 문서 문장은 개조식 평서문(`~한다`, `~이다`)이다. `foot` 의 "읽는 법"도 같은 문체로 쓴다.
- 배포 전 변경은 `(신규)`, `미배포` 로 표시한다.
- `meta.basis` 에는 근거 범위를 쓴다(읽은 코드, 조회한 DB 스키마, 실제 사례). 가상 예제이면 가상임을 쓴다.

## 확인

- `render.py` 는 id 중복, 존재하지 않는 `ref`·`from`·`to`, 잘못된 `tone`·`tag`·`op`, 행의 칸 수 불일치, 줄번호를 `ERROR:` 로 막는다.
- 스크린샷은 문서가 길어 `--size 1100,4400` 처럼 세로를 키워서 찍는다. 관계도의 선이 박스 뒤로 지나가는지, 컬럼 사전의 열이 맞는지, 흐름 표의 칸이 어긋나지 않는지를 본다.
- 관계도는 원래 크기(CSS px)로 그려지며 `−` `+` `100%` `맞춤` 컨트롤이 있다. 화면보다 넓으면 관계도 영역 안에서만 가로 스크롤한다.
