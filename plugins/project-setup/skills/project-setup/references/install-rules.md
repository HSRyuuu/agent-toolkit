# rules — 영역별 코딩 규칙

모듈·영역마다 에이전트가 따라야 할 코딩 규칙을 `.claude/rules/<area>.md`로 둔다. **코드에서 실제로 확인한 관례만** 적는다. 일반론(“가독성 좋게”)은 적지 않는다.

## 대상

| 자산 | 위치 | 원본 |
| --- | --- | --- |
| 영역 규칙 | `.claude/rules/<area>.md` | `templates/rules/RULES.md` |

영역은 프로필의 모듈과 스택으로 정한다. 예: `backend` (Spring Boot·Kotlin), `frontend` (Next.js), `e2e-testing` (Playwright). 단일 스택 작은 프로젝트는 파일 하나(`<stack>.md`)면 충분하다. 어떤 영역을 만들지 먼저 보여 주고 고르게 한다.

## 절차

1. 영역마다 대표 파일 5~10개를 읽는다. 같은 종류(컨트롤러, 서비스, 컴포넌트, 훅, 테스트)를 여러 개 비교해야 관례가 보인다.
2. `RULES.md`를 복사하고 토큰을 채운다.

| 토큰 | 채우는 값 |
| --- | --- |
| `{AREA}` | 영역 이름 |
| `{AREA_PATHS}` | 적용 경로 (예: `backend/src/main/kotlin/**`) |
| `{STACK_LINES}` | 언어·프레임워크·주요 라이브러리와 버전 (매니페스트 기준) |
| `{LAYOUT_ROWS}` | 레이어별 위치·명명 규칙과 근거 파일 |
| `{CODING_RULES}` | 반복해서 보이는 관례 (DI 방식, 예외 처리, DTO 변환, 상태 관리, 스타일링 방식 등). 규칙마다 근거 파일 하나 |
| `{TEST_RULES}` | 테스트 위치, 프레임워크, 명명, 실행 명령 |
| `{DONT_RULES}` | 코드에서 의도적으로 피하는 패턴이 보이면 적는다. 근거가 없으면 섹션을 지운다 |

3. 관례가 둘 이상으로 갈려 있으면(옛 방식과 새 방식 공존) 어느 쪽을 따를지 사용자에게 묻고, 답한 쪽만 규칙으로 적는다.
4. 진입점 `### 외부문서`에 파일마다 한 줄을 등록하고, `## 문서 매핑` 바로 아래에 다음 규칙 줄을 넣는다.

```markdown
- 코드를 수정하기 전에 해당 영역의 `.claude/rules/<area>.md`를 읽는다.
```

## 하지 말 것

- 확인하지 않은 규칙을 지어내지 않는다. 규칙 한 줄에 근거 파일 하나가 있어야 한다.
- 린터·포매터가 이미 강제하는 규칙(들여쓰기, 따옴표)은 적지 않는다. 대신 그 명령을 진입점 `## 명령어`에 둔다.
- 기존 `.claude/rules/` 파일이 있으면 덮어쓰지 않는다. 빠진 규칙만 제안한다.
