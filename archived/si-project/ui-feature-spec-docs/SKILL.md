# ui-feature-spec-docs — 화면별 기능 정의서 작성 스킬

프론트엔드 소스의 라우터·페이지 구조와 선택적 화면정의서(docx/pdf)로 **화면별 기능 정의서**를 단일 markdown으로 만든다. 라이브 브라우저 검증은 보조 모드다.

프레임워크 감지, 라우터 파싱(Vue Router, React Router, Next.js, Nuxt, SvelteKit, Angular), 클릭·submit·fetch 같은 기능 후보 추출은 모델이 이미 안다. 아래는 이 문서 형식과 판정 규칙만 적는다.

## 원칙

- **메인 입력은 소스 + 정의서.** 둘 중 하나만 있어도 동작하고, 둘 다 있으면 교차 매핑한다.
- **라이브 브라우저는 보조 모드, 기본 OFF.** 소스가 없거나 권한·feature flag·조건부 렌더링 검증이 필요하고 사용자가 요청했을 때만 켠다.
- **단일 파일 출력.** 화면이 몇 개든 하나의 markdown(기본 `./ui-feature-spec.md`)에 목차로 통합한다.
- **시작 1회 입력 수집, 이후 무질문.** 모호한 건 결과물에 마커로 보존하고 받아본 뒤 사용자가 결정한다.
- **발명 금지.** 어느 소스에도 없는 기능을 채우지 않는다. 빈 칸은 `(TBD)`.
- **세 소스는 동등한 증거다.** 소스=있을 수 있는 기능(조건부·dead code 포함), 정의서=있어야 하는 기능의 의도, 라이브=실제로 보이는 기능. 서로 덮어쓰지 않고 충돌은 마커로 남긴다.

## 입력 (한 번만 묻는다)

- 필수: 소스 경로(라우터 파일 또는 `app/`·`pages/`·`src/routes/`) 또는 정의서(`.docx`/`.pdf`) 중 최소 하나.
- 선택: 출력 경로, 프로젝트명·작성자(비우면 플레이스홀더). 프레임워크 감지가 실패할 것 같으면 이때 함께 묻는다.
- 라이브 보조 모드 ON일 때만 추가: base URL, 로그인 여부(로그인이면 테스트 계정 또는 사전 로그인 세션을 시작 시점에 받는다. **받지 못하면 라이브를 OFF로 강등**), 검증할 role, 동적 segment 샘플(`/users/:id → id=1`, 없는 경로는 스킵).

## 기능 ID

`UI-{feature-name}-{3자리 번호}`. `feature-name`은 화면명을 영문 의미 단어로 옮겨 kebab-case로(`사용자 목록` → `user-list`). 번호는 화면 안에서 `001`부터이고 화면명이 namespace라 화면 간 충돌이 없다. 한글을 ID에 쓰지 않는다. 동적 segment는 경로에는 그대로(`/users/:id`), 화면명에는 의미 단어로("사용자 상세"). 중첩 라우트는 평탄화하고 화면명에 계층을 반영한다("설정 > API 키").

## 정의서 파싱

```bash
pip install -r <skill>/scripts/requirements.txt
python3 <skill>/scripts/parse_design_doc.py <문서 경로> --output /tmp/design_doc.json
```

`<skill>`은 이 SKILL.md가 있는 디렉토리의 절대 경로다. JSON에서 화면 섹션은 다음으로 식별한다: "화면명:"·"Screen:"·"##"·"■"·"▣"로 시작하는 텍스트, "기능·기능명·설명·동작·이벤트"가 헤더에 든 표, 같은 화면명이 반복되면 그 사이를 한 섹션으로, 페이지 경계가 명확하면 페이지 단위. **추출에 실패해도 묻지 않는다.** 추출 못 한 raw 텍스트를 문서 끝 `## 부록 — 정의서 매핑 불가 영역`에 그대로 보존한다.

## 라이브 보조 모드 (ON일 때만)

필요한 정보가 모두 모였을 때만 실행하고, 부족하면 전체를 건너뛴다. Playwright MCP나 chrome-devtools MCP 중 설치된 것을 쓴다. 화면마다 navigate → 로딩 대기 → 접근성 스냅샷으로 `button`, `a[href]`, 입력·폼, `dialog/menu/tab`, 테스트 훅을 수집하고 콘솔·네트워크로 초기 API를 모아 "예상 동작"을 보강한다.

- **클릭·폼 제출 같은 인터랙션은 하지 않는다.** 데이터 변경 위험이 있다. Step 0에서 사용자가 명시적으로 허용한 경우만 한다.
- 추측한 URL로 접속하지 않는다. 실패는 전체를 중단하지 않고 마커를 달아 계속한다(접속 실패 `⛔ 라이브 검증 실패`, 로그인 리다이렉트 `🔐 인증 필요로 검증 스킵`, 빈 화면은 콘솔을 부록에 보존하고 `⛔ 런타임 에러`, 샘플 없는 동적 경로 `🔐 샘플 미제공으로 스킵`). 여러 role이면 role별로 분리해 비고에 명시한다.
- 라이브에서 안 보인다고 dead code로 단정하지 않는다. 권한·feature flag일 수 있으니 `🔒 조건부 표시`.

## 교차 매핑

사용자에게 보고하지 않고 결과를 문서에 바로 반영한다. 화면 단위 매칭 기준은 경로 일치 → 화면명 일치(라우트명·컴포넌트명 ↔ 정의서 제목 ↔ 라이브 `<title>`/`<h1>`) → 부분 일치 휴리스틱 순이다. **신뢰도가 낮으면 묻지 말고** `⚠️ 매칭 신뢰도 낮음`을 달고 양쪽 후보를 같은 섹션에 모두 보존한다. 매칭된 화면 안의 기능 항목에도 같은 분류를 적용한다.

| 소스 | 정의서 | 라이브 | 표기 |
|---|---|---|---|
| ○ | ○ | ○(또는 OFF) | 정상 (마커 없음) |
| ○ | ○ | X | `🔒 조건부 표시` 또는 `⛔ 라이브 검증 실패` (사유에 따라) |
| ○ | X | ○ | `📝 spec 누락` |
| X | ○ | ○ | `🧩 외부 구성` (서드파티·iframe 의심) |
| ○ | X | X(또는 OFF) | `⚠️ 미사용 의심` |
| X | ○ | X(또는 OFF) | `🚧 미구현` |
| X | X | ○ | `🔍 정적 추출 누락` |

라이브 OFF면 `🔒/📝/🔍/🧩/⛔/🔐` 마커는 쓰지 않는다. 추가 마커는 `(TBD)`(어느 소스에도 정보 없음).

## 출력

표 컬럼은 **라이브 OFF=5컬럼, ON=6컬럼(출처 추가)으로 고정**이고 임의로 바꾸지 않는다. 마커는 비고 또는 `출처` 컬럼에 표기한다. 특수 화면은 섹션 첫 줄에 한 줄 주석을 둔다(`> 🚧 미구현 — 정의서 p.14 기준으로만 작성됨`).

```markdown
# 화면 기능 명세서

| 항목 | 내용 |
|---|---|
| 프로젝트명 | {프로젝트명} |
| 작성일 | {YYYY-MM-DD} |
| Framework | {감지된 framework} |
| 화면 수 | {N} |
| 라이브 검증 | OFF (또는 ON, base=..., role=admin) |

## 목차
- [사용자 목록](#사용자-목록)

## 사용자 목록

- **경로**: /users
- **라우트명**: UserList
- **파일**: `src/views/UserList.vue`
- **설명**: 사용자 목록을 검색·정렬·페이징하여 보여주는 화면

### 기능 목록

| 기능 ID | 기능명 | 설명 | 트리거 | 예상 동작 |
|---|---|---|---|---|
| UI-user-list-001 | 사용자 검색 | 키워드로 사용자 필터 | 검색 버튼 / Enter | 검색 API 호출, 결과 테이블 갱신 |
| UI-user-list-002 | 사용자 정렬 | 컬럼 헤더 클릭 시 정렬 토글 | 컬럼 헤더 클릭 | (TBD) |
```

6컬럼일 때는 `출처`에 `✅ 소스+정의서+라이브`, `🔒 조건부 표시 (admin role)`, `📝 spec 누락` 같은 값을 쓴다. 문서 끝에는 `## 변경 이력`(버전·일자·작성자·변경 내용), `## 검증 메타`(Framework, 라이브 검증 여부와 시각, 동적 segment 샘플), `## 부록 — 정의서 매핑 불가 영역`을 둔다.

**같은 경로에 파일이 이미 있으면 묻지 말고 자동 백업한다.** 원본을 `{stem}.{YYYYMMDD-HHMMSS}.bak.md`로 이름 변경한 뒤 새 파일을 쓴다. 여러 파일로 나누는 것은 사용자가 요청했을 때만 한다.
