# api-spec-docs — API 명세서(규격) 생성 스킬

백엔드 소스(Controller/Router + DTO)를 읽어 **FE에게 전달하는 API 규격서 한 장**을 만든다. Postman 응답 예시와 링크를 대신하는 **규격서**이지, 작업 인수인계나 설계 배경 문서가 아니다.

프레임워크별 엔드포인트·파라미터 추출(어노테이션, 라우터 중첩 등)은 모델이 이미 안다. 아래는 이 문서 형식을 지키는 규칙만 적는다.

## 원칙

- **규격만 쓴다.** 요청 스펙 / 응답 스펙 / 에러. 배경, 설계 의도, 구현 히스토리, 검증 서사는 쓰지 않는다.
- **표가 본문, 산문은 예외.** 필드 정보는 전부 표 컬럼에 넣는다. 표 밖 산문은 `## 도메인 규칙`에만 둔다.
- **단일 markdown 출력.** 엔드포인트가 몇 개든 하나의 `.md`(기본 `./api-spec.md`). git diff로 API 변경을 리뷰하려는 포맷이다.
- **발명 금지.** 소스에 없는 필드·에러·설명을 채우지 않는다. 모르면 `(TBD)`, 유추했으면 `⚠️ 추론`.
- **시작 1회 입력 수집, 이후 무질문.** 모호한 건 결과물에 마커로 보존하고, 받아본 뒤 사용자가 결정한다.
- **분량 상한.** 엔드포인트 하나는 `Request 표` + `Response 표` + `예시 JSON 1~3개` + `Errors 표`가 전부다. 그 밖의 설명은 필드 `설명` 컬럼 한 구절, `## 도메인 규칙` 한 줄, 또는 삭제. 블럭 안의 표 밖 산문은 합계 2줄까지.

## 독자는 FE다

명세서가 실패하는 흔한 방식은 틀린 정보가 아니라 **백엔드 내부 사정으로 문서가 채워지는 것**이다. FE가 읽고 행동이 바뀌지 않는 정보는 빼거나 결과로 번역한다.

| 쓰지 않는 것 | 대신 쓰는 것 |
|---|---|
| DTO·클래스·메서드명 | 응답 JSON에 보이는 필드 경로와 관측 결과 |
| 어노테이션·프레임워크 설정 위치 | "값이 없으면 키가 생략됩니다" / "비로그인도 호출 가능합니다" |
| DB 테이블·컬럼·SQL | 그 필드가 언제 오는지를 FE가 볼 수 있는 말로 |
| 내부 설정 키·i18n 키 | 지금 내려가는 값과 그 안정성 (`type`으로 분기, `title`은 변할 수 있음) |
| 유틸·밸리데이터·리포지토리·배치 클래스명 | 입력 → 응답 판정 표 |
| 티켓 진행 상황, 기획 확인 대기, 리뷰 결과, 배포 순서 | (쓰지 않는다 — 규격이 아니다) |

예외는 하나다. **FE의 행동이 그 근거에 달려 있으면** 남긴다. `sort`가 `null`로 내려간다는 사실은 필요하지만, 그것이 어떤 어노테이션 때문인지는 필요 없다.

소스 근거는 엔드포인트 표의 `소스` 컬럼 한 곳에만 둔다(`파일명#메서드명`, 라인번호는 병기만).

## 입력 (Step 0, 한 번만)

근거 하나면 시작한다. 여러 개면 우선순위 `소스코드 > 기존 명세·실측 응답 > 합의된 계획·결정` 순으로 쓰고 낮은 것으로 보완한다.

| 근거 | 메타 표 `기준` 행 |
|---|---|
| 구현된 코드 | `소스코드` |
| 기존 명세·실측 응답 | `기존 명세` |
| 구현 전 계획 | `계획 (구현 전) — 구현 후 재검증 필요` |
| 변경 결정만 | `변경 결정` |

코드로 확인하지 않은 문서를 코드 기반처럼 읽히게 두지 않는다. 근거가 코드가 아니면 추출 절차를 건너뛰고 근거의 method·path·필드를 그대로 목록화한다. 근거에 없는 인증·권한·전역 에러는 행을 만들지 않는다. 근거가 **변경 결정만**이면 delta 블럭만 쓴다.

선택 입력(안 주면 기본값): 범위(기본 전체), 출력 경로(기본 `./api-spec.md`), 대상 티켓, 내부 API 포함 여부(admin·batch·actuator, 기본 제외하고 제외 목록은 부록에).

**메타 표에 빈 칸을 만들지 않는다.** 값을 모르는 항목은 행 자체를 만들지 않는다.

## 필드 표기

### 요청

- 파라미터는 위치(path/query/header/body)별로 표 한 행씩.
- **헤더는 그 엔드포인트의 동작을 바꾸는 것만** 적는다(누락 시 에러, 응답을 가르는 값, 인증). 모든 요청에 붙는 관용 헤더는 적지 않는다.
- 필수 `Y/N`은 **요청 표에서만** 쓴다. enum은 값을 전부 나열한다(`PENDING | PAID | CANCELED`). 제약(`1~99`, `최대 50자`)은 설명에 병기한다.

### 평탄화(dot-path)

DTO를 재귀 순회해 필드 하나를 표의 한 행으로 편다: `user.address.zipCode`, `items[].productId`, `matrix[][]`, `attributes.{key}`. 최대 depth 4(초과하면 타입명만 적고 `⛔ depth 제한`), 순환 참조는 첫 재등장에서 멈추고 `⛔ 순환 참조`.

### 응답: `필수` 대신 `존재`

응답 표에서 `필수 N`은 "생략 가능"·"null일 수 있음"·"특정 조건에서만"을 한 글자로 눌러버린다. 응답 성격의 표는 **전부** `존재` 컬럼을 단다. 상위 래퍼 표에서 빠뜨리지 않는다.

| 값 | 의미 |
|---|---|
| `항상` | 어떤 응답에서도 반드시 존재 (값이 `null`이어도 키는 온다면 `항상`) |
| `조건부: {조건}` | 조건을 그 자리에 쓴다 |
| `없음` | 스키마에는 있으나 이 엔드포인트에서는 절대 안 내려감 |

- **부모가 조건부면 자식은 `조건부: {부모} 존재 시`.** 부모만 조건부고 자식이 `항상`이면 읽는 쪽이 null 체크를 뺀다.
- **조건은 FE가 관찰할 수 있는 말로 쓴다.** 요청 값으로 갈리면 그 값을(`source가 PARTNER 계열일 때`), 응답의 다른 필드로 판별되면 그 필드를(`type=PARTNER_PICK`), 서버 내부 판정이면 `서버 판정 — 키 존재 여부로만 분기`. "실제 대상자가 있을 때만" 같은 백엔드 서술은 쓰지 않는다.
- 요청 값으로 갈리는 조건이 2개 이상이면 **입력 → 응답 판정 표**를 따로 만든다. 산문 세 줄보다 표 한 장이 정확하다.
- 요청 표를 복사해 응답 표를 만들면 `필수` 컬럼이 남는다. 응답 표에 `필수`가 남아 있으면 그 표는 다시 쓴다.

### 공유 스키마 hoisting

2개 이상 엔드포인트가 같은 객체를 반환하면 `## 공통 스키마`로 올리고, 엔드포인트 섹션에는 차이만 쓴다. 공통 응답 래퍼(`ApiResponse<T>` 등)도 한 번만 쓰고 엔드포인트 표에는 `data.` 이하만 적는다. 공통 스키마에 올라가는 것은 래퍼, 공유 객체 표, 둘 이상이 공유하며 동작을 바꾸는 헤더, 전역 에러 코드, 페이지네이션, 날짜·타임존 포맷뿐이다. **직렬화 규칙 섹션은 만들지 않는다.**

### 에러

그 메서드가 **실제로 던지는 것**만 엔드포인트 Errors 표에 적고, 전역 공통 에러는 공통 스키마로 뺀다.

## 도메인 규칙

필드 표로 표현되지 않지만 FE가 지켜야 하는 규칙은 **`## 도메인 규칙` 한 섹션**에 번호를 매겨 모은다. "FE 영향"·"주의"·"계약" 같은 이름으로 흩뿌리지 않는다.

들어가는 것: 분기 기준(`type`으로 분기, `title`은 번역값), 서버가 계산하지 않는 값, 서버가 정하지 않는 표시 순서, 목록의 순서·구성, 값의 산출 기준(웹은 세금 미포함가), 노출·부재 조건, FE가 만들어야 하는 것(아이콘, 상태별 문구).

규칙 하나는 **제목 한 줄 + 본문 최대 2줄**. 근거·배경·검증 이야기는 쓰지 않는다. 필드 표의 `설명`으로 충분하면 규칙으로 올리지 않는다.

## full / delta 판정 (내부 판단)

엔드포인트별로 전체 명세(full)와 변경분(delta)을 정한다. 문서에 "모드"로 표기하지 않고, 사용자에게 묻지 않는다.

| 조건 | 범위 |
|---|---|
| 근거가 `변경 결정`뿐 | delta (근거에 없는 필드를 채워 full로 늘리지 않는다) |
| 첫 생성이거나 기존 문서에 없던 엔드포인트 | full |
| breaking 신호가 하나라도 있음 | full |
| 변경 필드가 그 엔드포인트 전체 필드의 30% 초과 | full |
| 그 외 non-breaking 소폭 변경 | delta |

**breaking 신호**(하나라도 걸리면 `Breaking: Y`): 응답 최상위 구조 변경, 필드 삭제·이름 변경, 타입 변경, 선택→필수 승격, enum 값 삭제(추가는 아님), path·method 변경, 인증·권한 강화. `Breaking`은 이 목록에 **기계적으로** 걸리는지로만 판정한다. "FE가 안 쓰니 괜찮다"는 판단을 섞지 않는다. 삭제 행이 있는데 `Breaking: N`이면 자기모순이다.

`## 이번 변경`의 필드 변경 표는 엔드포인트별 `### {METHOD} {path}` 소제목으로 쪼갠다. 여러 엔드포인트가 공유하는 객체가 바뀌면 `### 공유 — {객체}` 하나에 표를 1회만 쓰고 영향 엔드포인트를 한 줄로 나열한다.

## 출력 형식

**형식의 기준은 이 템플릿 하나뿐이다.** 같은 프로젝트에 다른 명세서가 있어도 그 형식을 본뜨지 않는다. 기존 문서에서는 **사실(필드·값·조건)만** 가져오고 섹션 구성·컬럼·표기는 이 템플릿을 다시 적용한다. 헤딩은 평문으로 쓴다(백틱·괄호가 있으면 목차 앵커가 깨진다).

최상위 `##` 섹션은 다음이 전부다: 메타 표 → 목차(메타 표 바로 아래) → `## 이번 변경`(갱신·티켓 한정일 때만) → `## 도메인 규칙` → `## 공통 스키마` → `## 엔드포인트`(도메인 단위 그룹) → `## 변경 이력`/부록. 재발행 사유 같은 문서 관리 사정은 `변경 이력`에만 쓴다. 제목에 `(최종)`·`(v2)` 같은 꼬리표를 붙이지 않는다.

```markdown
# {프로젝트명} API 명세서

| 항목 | 내용 |
|---|---|
| 작성일 | {YYYY-MM-DD} |
| 기준 | {소스코드 / 기존 명세 / 계획 (구현 전) — 구현 후 재검증 필요 / 변경 결정} |
| 엔드포인트 수 | {N} |

> **범위** — {무엇만 다루는지 / 무엇이 범위 밖인지} 한 줄.

## 목차
...

## 이번 변경

| 엔드포인트 | 변경 | Breaking |
|---|---|---|
| `POST /api/v1/orders` | `memo` 추가 | N |

### POST /api/v1/orders

| 구분 | 위치 | 필드 | 변경 전 | 변경 후 |
|---|---|---|---|---|
| 추가 | body | `memo` | - | string / 선택 / 최대 200자 |

## 도메인 규칙

**① 주문 상태 분기는 `status`로 합니다**
`statusText`는 로케일에 따라 바뀝니다.

## 공통 스키마
(래퍼, 전역 에러 코드, 페이지네이션 ...)

## 주문

### POST /api/v1/orders — 주문 생성

주문을 생성하고 결제 대기 상태로 만듭니다.

| 인증 | 권한 | 상태 | 소스 |
|---|---|---|---|
| 필요 | MEMBER | 정상 | `OrderController.kt#create:42` |

#### Request

| 위치 | 필드 | 타입 | 필수 | 기본값 | 설명 |
|---|---|---|---|---|---|
| body | `items[].qty` | int | Y | - | 1~99 |

(예시 JSON)

#### Response 200

| 필드 | 타입 | 존재 | 설명 |
|---|---|---|---|
| `data.order_id` | string | 항상 | 주문 번호 |
| `data.coupon.items[].code` | string | 조건부: `coupon.items` 원소가 있을 때 | 쿠폰 코드 |

(예시 JSON)

#### Errors

| HTTP | code | 조건 |
|---|---|---|
| 409 | OUT_OF_STOCK | 재고 부족 |
```

- 필수 헤더가 2개 이상이거나 누락 시 에러가 나면 Request 표 아래에 `curl` 한 줄을 붙인다.
- **delta 블럭**은 바뀐 행만 담는다(`구분 | 위치 | 필드 | 변경 전 | 변경 후`). `변경 전`은 기존 문서에서 읽고 확인 불가면 `(TBD)`. FE가 코드를 고쳐야 하는 변경이면 그 규칙은 `## 도메인 규칙`에 넣는다.
- full로 판정되면 엔드포인트 섹션 전체를 같은 템플릿으로 다시 쓴다. 사유는 `변경 이력`에만 적는다.

### 예시 JSON

- 표의 타입·제약과 모순되지 않는 값만, enum은 첫 값.
- 운영 데이터·사번·회사 식별자·토큰을 넣지 않는다. `P-001`, `ORD-001` 같은 중립 더미를 쓴다. 로컬에서 실측한 응답을 붙일 때 실제 상호·상품명·사람 이름·운영 ID가 새기 쉽다.
- `null`이면 키가 빠지는 API는 선택 필드를 **키째 뺀다**. 그렇지 않으면 `null`로 남긴다. 진짜 근거는 `존재` 컬럼이다.
- **전량이 아니라 전 분기.** 배열은 서로 다른 분기를 보여주는 대표 원소 2개까지, 나머지는 `// ... 동일 구조 N건 생략`. 빈 상태(`items: []`)는 별도 짧은 예시. 엔드포인트당 예시는 3개까지, 더 필요하면 분기를 표로 옮긴다.

| `⚠️ 추론` | 이름·관례로 유추한 값 |
| `🚧 미구현` | 스텁·TODO·FIXME가 달린 엔드포인트 |
| `🗑 deprecated` | `@Deprecated`, 또는 소스에서 사라진 엔드포인트 |
| `⛔ depth 제한` / `⛔ 순환 참조` | 평탄화 중단 |

## 갱신

출력 경로에 문서가 이미 있으면 전체를 재생성하지 않는다. 엔드포인트별로 full/delta를 판정하고, 변경 없는 엔드포인트는 문장도 다시 쓰지 않는다. 사람이 채운 내용(`(TBD)`를 채운 설명, 비고)은 덮어쓰지 않는다. 소스에서 사라진 엔드포인트는 지우지 말고 `🗑 deprecated`로 남긴다. `## 이번 변경`을 새로 쓰고 `변경 이력`에 행을 추가한다.

## 쓴 뒤 확인

- 응답 성격의 표에 `필수` 컬럼이 남아 있지 않은가. `존재` 컬럼이 빠진 응답 표(특히 상위 래퍼)는 없는가. `조건부`인데 조건이 없거나 FE가 관찰할 수 없는 서술인가.
- 부모가 `조건부`인데 자식이 `항상`인 행이 없는가.
- 클래스·어노테이션·테이블·SQL·설정 키가 본문에 남아 있지 않은가(남겼다면 FE의 행동이 바뀌는 이유인가).
- 엔드포인트 블럭이 `Request / 예시 / Response / 예시 / Errors` 밖으로 늘어나지 않았는가. FE 규칙이 `## 도메인 규칙` 한 곳에 모였는가.
- 메타 표에 값 없는 행이 없는가. 코드로 확인하지 않았는데 `기준`이 `소스코드`로 적혀 있지 않은가.
- 최상위 `##` 섹션이 위 목록 밖으로 늘어나지 않았는가. 목차 앵커가 실제 섹션과 맞는가.
- 표와 예시 JSON이 서로 모순되지 않는가. enum이 값 나열 없이 `enum`으로만 적힌 행이 없는가.
- 예시에 실제 상호·이름·운영 ID가 남아 있지 않은가.
- (갱신) delta로 둔 엔드포인트에 breaking 신호가 없는가. delta 표에 안 바뀐 행이 섞이지 않았는가.
